01

What it does

A Family Guy clip goes in. What comes out is a 9:16 video where the top half is a Desmos graphing calculator drawing the scene as line art, expression list visible, while the original clip plays underneath.

The pipeline is fully automatic. autopilot.py --count 10 finds ten clips online, works out which episode each is from, rejects the ones it cannot caption, renders them, posts them to YouTube, and leaves copies plus captions in a folder. No framework — ~4,100 lines of Python across 10 modules, leaning on yt-dlp, faster-whisper, playwright, opencv, numpy and ffmpeg.

02

How it draws

The clip is decoded to grayscale frames, edges are traced to polylines, simplified, and packed into list-valued parametric expressions. A single slider n selects the frame.

Desmos caps how long a list can be, so frames are packed into chunks. Each chunk is gated by an expression that evaluates to 1 inside its own frame range and is undefined outside it. An undefined gate blanks that chunk's curve without disturbing any index arithmetic — so every chunk can keep using the same clamped index without special-casing the boundaries.

G₁ = {1 ≤ n ≤ 10 : 1}
The gate. Defined only while the slider sits inside this chunk. Everywhere else it is undefined, which silently blanks the curve.
J₁ = min(max(n − 0, 1), 10)
The clamped index. Always a valid position in the list, even when the slider is far outside this chunk — so nothing ever indexes out of range.
R₁ = [O₁[J₁] … E₁[J₁]]
The stroke range. Slices this frame's strokes out of the chunk's offset and end lists.

Move the slider and exactly one chunk is defined at a time. The rest evaluate to nothing and disappear:

Slider n = 14
Chunk C₁ — frames 1–10
G₁ undefined → curve blank
Chunk C₂ — frames 11–20
G₂ = 1 → this chunk draws frame 14
Chunk C₃ — frames 21–30
G₃ undefined → curve blank

The finished graph is then screenshotted frame by frame in a headless Chromium and stacked over the source clip with ffmpeg. That screenshot loop is where all of the time goes — which took a while to notice.

The number that matters most is the smallest one: mean watch per play is 18.9 s. Several of these clips run 9–16 seconds, so a mean above 18 s means viewers are looping them. That is precisely the signal short-form ranking rewards, and it is the strongest thing in the dataset.

The distribution is the story

Three posts are four-fifths of everything. Seventy-one of them are a rounding error. Median post: 6.82 hours. Mean post: 155 hours — a 23× gap.

04

The model that didn't exist

The original goal was a model that picks clips to maximise views. That model was built, measured, and does not exist.

A retention model is real and works out of sample — cross-validated R² = 0.49. But it turns out to be duration in disguise, and duration does not separate winners from losers: the top ten posts by plays run 8–32 s and the bottom ten run 6–40 s.

Correlation with plays — and what happens when you try to predict them directly
RelationshiprReading
Predicted retention → plays +0.02 Nothing. Not "weak but positive" — nothing.
Measured retention → plays+0.40Real, but only measurable after posting
Duration → plays−0.15Noise
Duration → retention−0.74Strong — which is why the model is duration in disguise

Predicting plays directly fails outright: cross-validated R² = −0.89, which means worse than guessing the mean every time. The part of retention that does predict plays is only measurable after a post is already live.

So the system does not pretend to forecast. It runs hard filters — length, captionability, dedupe — which do the real work; it records one external signal, the view count the original uploader got, explicitly labelled an untested hypothesis with the test written and currently reporting n = 0; and then it leans on volume. Hit rate is about 4.9%, so ten clips is roughly a 40% chance of one breakout. When nothing predicts the shots, more shots beats better shot selection.
05

Bugs that looked like normal operation

Each of these was found the same way: a measurement contradicted an assumption that had never been checked.

The renderer was optimised in the wrong place

The tracer runs a pool of 8 worker processes on a 15-core machine, so "use more cores" was the obvious speedup. Profiling one 13.8 s clip (331 frames) said otherwise — making tracing instantaneous would have saved 4%. The bottleneck was a single Chromium page screenshotting one frame at a time at 486 ms per frame.

…and it had been quietly producing wrong frames the whole time

Parallel capture produced frames that differed from serial. Rather than assume the new code was broken, the serial path was tested for determinism — and it was perfectly deterministic, which is exactly what had hidden the bug.

The settle logic accepted the canvas as finished after 2 unchanged animation frames, about 33 ms. Desmos pauses longer than that in the middle of an update, so the screenshot was catching the background redrawn and the character not. Ground truth was established by raising the threshold until the output stopped changing — stable=12 and stable=24 are byte-identical, so 12 is converged.

It was invisible because it was consistently wrong. A performance investigation turned up a correctness bug that had been shipping for months, and the fix made the output both faster and right — not a trade between them.

The harvester was blind to Shorts

yt-dlp --flat-playlist reports duration: None for every YouTube Short. The filter read if not vid or not dur: continue, so it silently discarded 100% of them — and Shorts are by definition under 60 s, which is precisely the 8–45 s band being searched for. The richest source was being dropped in full, and it printed 40 results, 0 in band, indistinguishable from a genuinely bad source.

Fixed by carrying unknown-duration entries through to the full metadata fetch. Candidate pool per run went from 81 to 120, up 48%, with 46 Shorts recovered in the first run afterwards.

Three more of the same shape

  • A curated source list that had never worked. Two channel handles were seeded by guessing instead of checking — one had no /videos tab, the other 404'd. A dead channel prints 0 results, identical to one that has simply been exhausted, so the entire curated half of the harvest contributed nothing for its whole existence. Dead sources now warn loudly.
  • The learning loop could not close. Performance data was keyed by Instagram's re-encoded copy and source data by render tag, so nothing joined them. Duration looks like the obvious join key and is not — 26 unique matches of 68, and tightening the tolerance makes it worse, because the re-encode shifts duration by more than a frame. Matching on dialogue n-gram overlap instead, with a required margin over the runner-up, links 56 of 68 at a median overlap of 0.95 and zero ambiguous.
  • Uploads went to the wrong channel. A Google account can own several YouTube channels and the consent screen has a channel picker that is easy to click through. The youtube.upload scope is write-only, so the tool could not read back where anything had gone. Fixed by adding youtube.readonly, asserting the channel handle before every upload, and verifying each video is live afterwards with a retry backoff.
  • Two independent daily limits. YouTube enforces an API project quota and a per-channel upload cap of about 26 a day. The second arrives as HTTP 400 and does not contain the word "quota", so a handler checking for it missed the cap entirely and burned 30 doomed attempts in a row.
06

Cost & timing

Clip length is the dominant cost lever

Render time scales with clip duration at roughly 11–12×, but the spread is real: 7.3× to 15.5× across the first batch, driven by how much frame-to-frame reuse the tracer finds. The first five measurements all landed between 10× and 13×, which made the constant look far tighter than it was.

Plays settle at 48 hours

Two insight fetches 53 hours apart, bucketed by how old each post already was. Posts past 48 hours grew a median of +0.7%.

Copyright, empirically

2 of 140 uploads were Content-ID blocked. Both were over 89 s. Nothing under 80 s was ever touched. The clip length cap is set at 45 s on that evidence, which costs nothing — the entire top ten by plays is under 32 s.

07

Honest limits

  • Seven days of data. 81 posts, one account, one content genre. Nothing here generalises to other niches, and every correlation is computed on a sample where three posts dominate all the aggregates.
  • The ranking signal is untested. Source popularity is a hypothesis. The test is written and currently reports n = 0. It has not been shown to work.
  • Instagram posting is manual. YouTube is fully automated; the platform that produced all 12,597 hours still needs a human to upload. The automation is genuinely incomplete.
  • yt-dlp is a single point of failure. The whole harvest stage depends on one external tool that breaks whenever YouTube changes. Failures are loud and skip the run rather than posting garbage.
  • Content-ID exposure scales with automation. Two of 140 were blocked; the 45 s cap is a mitigation, not a guarantee.
